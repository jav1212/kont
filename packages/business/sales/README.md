# `@kontave/sales`

Sales application and domain contracts, including controlled offline draft synchronization.

## Emisión de factura con serie documental (ADM-017, ADM-018 y ADM-019)

`IssueSalesInvoiceWithDocumentSeries` confirma una factura de venta en borrador y asigna su número de serie dentro de la misma transacción. Acepta una serie seleccionada explícitamente o la regla configurada para el alcance empresa/sucursal y requiere una clave de idempotencia. Un reintento idéntico devuelve la asignación inmutable original; una reutilización incompatible de la clave falla.

El adaptador Supabase usa la RPC exclusiva de servidor de [`328_sales_invoice_document_series_issuance.sql`](../../../supabase/migrations/328_sales_invoice_document_series_issuance.sql), endurecida por [`329_sales_invoice_document_series_type_guard.sql`](../../../supabase/migrations/329_sales_invoice_document_series_type_guard.sql). La asignación se registra en una tabla privada con RLS, ligada tanto a la factura como a la serie, y la confirmación revierte por completo si falla la caja o cualquier otra condición posterior a la selección. El [smoke reversible](../../../supabase/checks/sales_invoice_document_series_issuance_smoke.sql) cubre emisión, replay, rechazo de tipo documental y rollback.

La variante IVA de `IssueSalesInvoiceWithDocumentSeries` prepara un hecho desde el borrador fiscal y exige que la persistencia confirme factura, número, snapshot fiscal y hecho en una RPC. Su contrato local vive en [`335_sales_series_tax_fact_issuance.sql`](../../../supabase/migrations/335_sales_series_tax_fact_issuance.sql); depende de las migraciones fiscales 321–323, 322/323 y del registro atómico 338. Esas migraciones se aplicaron al proyecto Supabase conectado. Como PostgreSQL truncó el identificador RPC original al límite de 63 bytes, el adapter usa el alias estable de [`368_iva_sales_rpc_name_compatibility.sql`](../../../supabase/migrations/368_iva_sales_rpc_name_compatibility.sql). MCP verificó que `service_role` puede ejecutarlo y `authenticated` no. Las pruebas del adapter validan el nombre y el payload; todavía falta conectar la confirmación Web al borrador previo a emisión y probar la transacción en Supabase. La salida no constituye una emisión mediante proveedor fiscal externo.

`PrepareConfirmedServiceInvoiceFiscalDocument.prepareDraftCandidate` y `POST /api/fiscal/sales/[id]/prepare?mode=atomic-candidate` permiten reconstruir, sin persistir, un candidato fiscal para un borrador de venta con líneas de producto y/o servicio clasificadas. `SalesInvoiceLineVatAdapter` resuelve cada tipo por su perfil y exige un catálogo de reglas versionado por empresa; las unidades de producto no soportadas fallan de forma segura. La respuesta incluye `sourceUpdatedAt`, que la RPC de emisión compara bajo bloqueo. El endpoint heredado sin ese modo sigue preparando desde facturas confirmadas. El candidato continúa limitado a VES y no admite impuesto financiero ni ajustes a nivel de cabecera.

El RPC histórico de 328 sigue disponible para los consumidores que aún no migran. La nueva ruta atómica exige que quien la invoque aporte una versión fuente, borrador fiscal con determinaciones guardadas, fecha y metadatos de reconocimiento; el paquete no inventa tasas ni resuelve reglas al confirmar.

## Emisión de nota de entrega con serie documental (ADM-017, ADM-018 y ADM-033)

`IssueSalesDeliveryNoteWithDocumentSeries` es el caso de uso portable para confirmar un borrador de nota de entrega y asignar una serie de empresa o sucursal en la misma transacción. Valida el ámbito de la serie, atribución comercial, selección por regla o explícita, clave de idempotencia y las opciones operativas de inventario. La nota de entrega no incorpora un documento fiscal ni un hecho de IVA.

`SupabaseSalesDeliveryNoteDocumentSeriesIssuanceRepository` prepara la llamada a `confirm_native_sales_delivery_note_with_document_series_secure`. La migración aditiva local [`367_sales_delivery_note_document_series_issuance.sql`](../../../supabase/migrations/367_sales_delivery_note_document_series_issuance.sql) define la RPC y una tabla privada de asignaciones inmutables exclusiva de notas; requiere primero las correcciones 365/366. La [integración PGlite](./test/integration/sales-delivery-note-document-series.integration.mjs) comprueba tipo documental, rollback de numeración, selección por regla o explícita, replay, conflicto de clave y último número. Sustituye la confirmación real por una dependencia controlada; no valida stock ni datos del proyecto conectado. El [preflight de series y datos](../../../supabase/checks/sales_delivery_note_series_preflight.sql) y el [preflight de funciones y triggers](../../../supabase/checks/sales_delivery_note_confirmation_contract_preflight.sql) deben ejecutarse antes en el esquema remoto: revisan asignaciones existentes, notas históricas y cuentas por cobrar/pagos, y devuelven las definiciones efectivas de confirmación y crédito. La corrección compatible [`365_sales_credit_receivable_invoice_only.sql`](../../../supabase/migrations/365_sales_credit_receivable_invoice_only.sql) limita nuevas cuentas por cobrar al tipo `venta` y conserva el bloqueo de desconfirmación para documentos históricos pagados; pasó una [integración PGlite descartable](./test/integration/sales-credit-receivable-document-type.integration.mjs), pero no se ha contrastado ni aplicado en Supabase.

Tras los preflights y las tres migraciones, el [smoke reversible de emisión](../../../supabase/checks/sales_delivery_note_document_series_issuance_smoke.sql) selecciona una nota borrador y un actor autorizados, crea una serie temporal, confirma mediante la RPC y verifica replay, numeración, ausencia de cuenta nueva y rollback ante fallo de caja. Requiere un borrador elegible; no crea ni modifica datos permanentes. El SQL pasó sobre un fixture PGlite con dependencias de confirmación simuladas, pero todavía no se ha ejecutado en el proyecto conectado.

La [integración conjunta PGlite](./test/integration/sales-delivery-note-credit-series.integration.mjs) ejecuta los cuerpos reales de 365–367, el trigger de crédito y la función histórica de confirmación de inventario de 264, enlazada mediante las funciones de atribución y caja de 277/278. Una nota de un cliente con deuda superior al límite confirma y recibe serie sin cuenta nueva, aun con importe de crédito legado; una factura excedida sigue denegada y otra dentro del límite crea su cuenta. Para un producto simple comprueba salida, saldo y rollback de número/stock cuando falta existencia. El adaptador `shared_inventory_movement_save` se simula en la prueba, por lo que esta evidencia no valida valoración, disparadores de movimientos ni el esquema conectado y no reemplaza el smoke en Supabase.

El SQL local de `confirm_web_sales_invoice_secure` suma el crédito nuevo sin comprobar `document_type`; por tanto, limitar el trigger de cuentas por cobrar no basta para una nota a crédito. La migración local [`366_sales_delivery_note_credit_limit.sql`](../../../supabase/migrations/366_sales_delivery_note_credit_limit.sql) propone que solo `venta` consuma el límite: conserva la autorización ordinaria, la serialización por cliente y la confirmación de inventario. Su [integración PGlite descartable](./test/integration/sales-delivery-note-credit-limit.integration.mjs) comprueba que una nota se confirma aun con deuda por encima del límite y que una factura excedida conserva el requisito de excepción. Esta política comercial es provisional hasta contrastarla con el contrato remoto y la decisión de producto. Supabase MCP volvió a responder `MCP authentication required`; no se ejecutaron los preflights, no se aplicaron las migraciones 365–367 ni se confirmó una nota de entrega en el proyecto conectado. No hay integración Web ni emisión operativa.

## Offline draft adapter boundary

`@kontave/sales/offline` exports browser adapters for an IndexedDB outbox, an IndexedDB key store, and a WebCrypto payload protector. The outbox stores only encrypted payloads and minimal routing/state metadata. Its `readwrite` transactions enforce operation idempotency, FIFO claims, lease recovery, and revision-checked settlement across tabs.

The key store persists non-exportable `CryptoKey` values by structured cloning in the browser profile. The protector encrypts payloads with AES-256-GCM, authenticates the actor/organization/company/branch/operation binding, and computes an HMAC-SHA-256 intent tag for stable deduplication. Applications should create one database name per product profile and should close adapters when their owning runtime shuts down.

These browser adapters do not replace a server authorization boundary. A future gateway must derive the actor from the current authenticated session, revalidate access and current commercial source data, and create only a draft using the original operation ID as its idempotency key. IndexedDB keys are non-exportable to ordinary JavaScript APIs, but same-origin code can request their use; this storage is not equivalent to iOS Keychain or Android Keystore. Native clients must provide their own protected key and durable outbox adapters.

`SupabaseOfflineSalesOrderDraftGateway` is the server-only persistence adapter for version-one merchandise-order drafts. It invokes the RPC from [`334_offline_sales_order_draft.sql`](../../../supabase/migrations/334_offline_sales_order_draft.sql), which revalidates the actor, active company, branch access, customer revision, and product price/currency/version before persisting a draft. The table is private under RLS and the RPC is exclusive to `service_role`; the [reversible smoke](../../../supabase/checks/offline_sales_order_draft_smoke.sql) verifies replay, product-price and customer-revision drift, duplicate lines, an unknown branch and denial.

`@kontave/sales` passed `check` and 99/99 tests for this cut.

The server draft remains a draft: it does not create an invoice or number, reserve or move stock, create a payment, or issue a fiscal document. There is no authenticated HTTP gateway or client composition yet, so this does not make offline sales available to users.

Offline queuing currently supports only `sales.order.draft.create`. Confirmation, stock reservation or movement, payment, fiscal issuance, and document numbering remain online-only. The adapters are package capabilities and are not composed into a production client yet.
